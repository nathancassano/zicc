# Hoisted array addresses and running pointers

When a loop walks through an array in equal steps, zicc can remember the current
address and add the same number of bytes each time. For a two-dimensional array,
one step might be a whole row. The compiler gets the step size from the element
or row type, including types named by a typedef or passed as an array parameter.
The loop's name and the array dimensions do not have to match a sample.

Existing function cursors now accept array-row strides. A loop-local pass then
collects complete element addresses, proves their other inputs invariant, and
initializes private near cursors after the first successful loop condition. Each
cursor advances by its byte coefficient times the induction-variable step.
Nested loops initialize their inner cursors anew on each outer iteration.

General supported bodies use two-byte cursor homes in the current stack frame.
This preserves ordinary handling of reads, writes, compound assignments, wide
values, overlapping input/output, conditions, `break` and `continue`. The original
C index retains its visible updates and final value. [Locally saved DP counters](dp-loop-counters.md)
can eliminate dead index updates or reconstruct an index at exit. Multiple accesses retain their own cursors and evaluation order.

A straight two-byte scalar assignment with a unit-incrementing index and a
direct word `<` condition keeps its single cursor in X. It emits the store and
constant pointer advance directly; the loop condition and C index updates remain.
Function-level cursors are synchronized at exit when the index is observed
outside the region. Other supported loops keep frame cursors.

The selector rejects calls, escaped scalar inputs, changing bases or invariant
indices, non-affine/discontinuous subscript expressions, nested bodies at the
current loop level, and unpredictable induction updates. Loop conditions must
be pure word expressions. Return-containing regions retain ordinary lowering.
Plans are bounded to eight addresses per loop and 32 loops per function and
respect the existing 768-byte frame budget. Pointer-chasing and unsupported
expression forms also retain ordinary lowering.

`--no-strength-reduction` disables both row cursors and loop-local affine cursors.
`--no-register-loops` retains affine frame cursors but disables X residency.
The runtime and calling convention are unchanged.

## Differential verification and measurements

`tests/check-affine-loops.py` executes the same sources in three configurations:
disabled strength/register optimization, affine frame cursors, and affine X
cursors. It checks SNES results against explicit expectations and MSVC references.
Coverage includes all multidimensional access fixtures, unsigned wrap, nonunit
and descending steps, `break`/`continue`, zero iterations, observable indices,
changing loop bounds, overlapping accesses, char/int/long/struct elements and
conservative fallbacks for calls, narrowing, changing rows/bases and nonlinear
steps. The existing strength suite runs it sequentially in the shared queue.

The four assignment kernels are compiled separately from an identical opaque
driver, without LTO. The driver checks the array contents after each call.
Mesen hooks assert kernel call counts, matrix/row/column/value arguments and
the exact number of byte writes for each invocation. Three emulator runs retain
identical per-call measurements, with three calls per kernel (six for the row
kernel, which also clears the matrix). All variants use the same FastROM, near
pointer ABI, RAM placement and required integer runtime. Timing hooks measure
only the called kernels, excluding driver validation.

Evidence is retained in `build/affine-loop-check/`: `results.json`, separate
kernel/driver C and assembly, ROMs, maps, labels, assertion scripts and raw logs.
Compiler, source, runtime and ROM hashes accompany the repeated timing samples.
`assembly.md` contains complete disabled/frame/X versions. The simpler assembly
report in `build/multidimensional-check/loop-assembly.md` is regenerated by the
existing multidimensional semantics check.

Measured master clocks per complete kernel call (three repeated emulator runs):

## Computation, data accesses and pointer work

The assignment kernels perform no arithmetic computation on their data: useful
work is one word load of `value` and one word store to the matrix. Inner row
loops use two `INX` instructions for pointer advancement; column loops use
`TXA; CLC; ADC #10; TAX`. Both keep seven instructions for the visible C index
update and signed loop condition. Those include an additional word load/store
of the index home on each iteration.

Instruction-level Mesen execution callbacks partition representative complete
calls as follows, in master clocks:

| Traversal | Useful load/store | All pointer work | Loop/index control | ABI/frame | Total |
|---|---:|---:|---:|---:|---:|
| Across row | 440 | 1350 | 902 | 430 | 3122 |
| Down column | 240 | 640 | 626 | 470 | 1976 |
| Nested rows | 1240 | 1924 | 3540 | 510 | 7214 |
| Nested columns | 1240 | 3120 | 4774 | 430 | 9564 |

Pointer work includes hoisted setup, the row multiplication helper where needed,
outer row-start updates and per-element advancement. ABI/frame covers parameter
homes, prologue, return preparation and epilogue. Timing includes instruction
fetches and WRAM accesses; refresh stalls remain attributed to their instruction
interval. Every partition sums exactly to its kernel timing. Three repeats
reproduce all recorded calls and partitions. `breakdown.json`, raw logs, Lua
callbacks, `profile.lst`, `instruction-categories.json` and the profiling script
are retained beside the other evidence in `build/affine-loop-check/`.

Final full verification passed 27/27 suites / 76 jobs in 278.44 seconds with
20 hardware-thread workers and all 200,873 arithmetic cases. Logs:
`build/check/20261106T132021.149000Z/`.
